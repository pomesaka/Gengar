# 要件決定ログ

要件定義フェーズの論点に対する決定を時系列で記録する。各決定は `docs/requirements.md` / `docs/functional-requirements.md` に反映される。本ファイルは「なぜその決定になったか」の理由と却下した代替案を保持する ADR 相当の記録。

> 記法: 各エントリは「**論点 / 決定 / 根拠 / 却下した代替案 / 反映先**」。

---

## 決定 1: 過去 JSONL の遡及取り込み

- **論点**: インストール時点で `~/.claude/projects/**/*.jsonl` に既に溜まっている過去セッションをどう扱うか
- **決定**: **オプトイン + 期間指定**。既定ではバックフィルしない。`gengar install --backfill=30d` のような期間指定、`--backfill=all` で全件。
- **根拠**:
  - 数 GB の過去 JSONL を無条件に読むのは導入時コストが高すぎる
  - 一方で「導入直後はダッシュボードが空」では価値が伝わらないため手段は提供したい
  - 期間指定があればユーザーが初回コストを制御できる
- **却下した代替案**:
  - A（全件自動取り込み）: 導入時に重すぎる
  - B（導入以降のみ、固定）: 過去を見たいユーザーを救えない
  - C（オプトインだが範囲指定なし）: 大量 JSONL を一気に取り込むしかなくなる
- **反映先**: `docs/requirements.md` §R4.1

## 決定 2-a: データ保持期間のポリシー

- **論点**: 生イベントをどの期間保持するか。固定か、設定可能か
- **決定**: **ユーザー設定可能。既定 90 日。`0` で無期限**
- **根拠**:
  - 個人利用のメトリクスとして 90 日は妥当な出発点
  - 長く保持したい／すぐ消したい双方のユーザーに対応したい
- **却下した代替案**:
  - A（無期限固定）: ストレージが無制限に増える
  - B（固定 90 日、変更不可）: 柔軟性がない
- **反映先**: `docs/requirements.md` §R4.2

## 決定 2-b: 生イベント削除後のロールアップ保持

- **論点**: 保持期間を過ぎて生イベントを削除した後、集計値 (日次/週次など) を残すか
- **決定**: **Y — 集計値は無期限保持**
- **根拠**:
  - R2.2「期間単位の切り口」は長期データがあってこそ価値が出る
  - ロールアップは 1 日 × プロジェクト数程度のサイズで極小。無期限でも問題ない
  - ccusage など他ツールが弱い「数ヶ月〜年単位のトレンド」を差別化要素にできる
- **却下した代替案**:
  - X（集計値も生イベントと同じ期限）: 長期トレンドが見えなくなる
- **反映先**: `docs/requirements.md` §R4.3

## 決定 3-a: 個別削除の要件化

- **論点**: 期間一括 (`prune`) に加え、特定セッション／プロジェクトの個別削除を要件に含めるか
- **決定**: **B — 個別削除を要件化**
- **根拠**:
  - 機密情報が意図せず収集された場合の救済として必須
  - 実装負荷は軽微（SQL の WHERE 句ベース）
  - プライバシー観点の信頼性を高める
- **却下した代替案**:
  - A（期間一括のみ）: 特定セッションの機密除去ができない
  - C（要件化しない）: プライバシー要件として弱い
- **反映先**: `docs/requirements.md` §R4.4

## 決定 3-b: エクスポート機能

- **論点**: CSV / JSON の一括エクスポート機能を要件に含めるか
- **決定**: **Q — Phase 1 ではスコープ外**
- **根拠**:

- **却下した代替案**:
  - P（要件化）: MVP に含めると工数が増える。ユーザー需要が立つまで保留
- **反映先**: `docs/requirements.md` §R4.5, §5.2

## 決定 4: 収集モード（メタデータのみ）

- **論点**: 本文の保存粒度を full / summary / metadata のどれにするか
- **決定**: **metadata のみ**。本文（プロンプト・応答・ツール結果の生テキスト）は**保存しない**。全レコードに `session_id` ラベルを付与し、本文参照が必要な場合はユーザーが `~/.claude/projects` 配下の JSONL を直接参照する前提とする。
- **根拠**:
  - Gengar の目的は **メトリクス** であり、会話本文の複製は目的外
  - JSONL が既にローカルに存在するため、本文を Gengar 側に複製する合理性が薄い
  - 本文を持たないことで、プライバシー要件が大幅に簡素化し、ダッシュボード API 経由の情報露出面積も最小化される
  - ユーザーが本文を見たい場合は session_id から JSONL を辿れば良い
- **却下した代替案**:
  - full（本文含む）: ストレージ肥大とプライバシーリスク
  - summary（先頭 N 文字 + ハッシュ + 長さ）: 中途半端。中身を見たいなら JSONL を見ればよく、メトリクスには不要
- **副次効果**:
  - F1.4.1 の 3 モード案は撤回され、単一モード（メタデータのみ）になる
  - 論点 5（シークレットマスクの強度）は **本決定により不要化**。ただしツール引数（`file_path`, Bash `command` 等）の扱いは別論点として保留 (F1.4.4)
  - F1.3 の一部メトリクス（編集ファイル数、Bash 実行回数の詳細）は、ツール引数の扱いが決まるまで算出方式が未確定
- **反映先**: `docs/requirements.md` §R1.2, §R1.5, §N2 / `docs/functional-requirements.md` §F1.3, §F1.4

## 決定 5: ツール引数の扱い

- **論点**: Edit の `file_path`、Bash の `command` などツール引数を保存するか
- **決定**: **原則 C — ツール引数は保存しない**。ただし **Bash ツールに限り、実行された外部プログラム名 (第一トークン、例: `rg` / `find` / `git` / `npm`) のみ保存**する。Bash 以外のツール (Edit, Read, Grep, Glob, WebFetch 等) は引数を一切保存しない。複数コマンドが `&&` / `;` / `|` で連結されている場合は各プログラム名を記録する。
- **根拠**:
  - ユーザー運用: worktree / workspace 分離で**同じ論理ファイルでもセッションごとに絶対パスが変わる**。パスの正規化を実装し始めると本質外の複雑性が急増する
  - 一方で「Claude が Bash 経由でどんな外部ツール (rg, find, git 等) を使っているか」は Phase 1 でも知りたい価値のある情報で、プログラム名はパスに依存しない（worktree 問題が起きない）
  - プログラム名はシークレット性が低く、保存リスクも小さい
  - 引数・オプションは保存しないため、ファイルパス・URL・トークン等の機密は漏れない
- **却下した代替案**:
  - A（全引数を生で保存）: シークレット混入リスク + worktree 正規化問題
  - B（ハッシュ化）: 検出ロジックは組めるがパスが変わると別物判定になり worktree 問題を解けない
  - C-strict（Bash 含め完全に引数なし）: 「rg / find / git を何回使ったか」すら見えず、粒度が粗すぎる
  - D（ホワイトリスト全般）: ツールごとに維持ルールが増え、Phase 1 には過剰
- **副次効果**:
  - F1.3 から「編集ファイル数、追加／削除行数」「Bash コマンド全文依存の集計」を除外
  - Bash メトリクスは「Bash 呼び出し回数／失敗数」+ 「プログラム名別の呼び出し回数」を Phase 1 で提供
  - F5.3 の自己改善ヒントから「同一ファイル繰り返し Read」「同一 Bash コマンドリトライ」などを Phase 1 では除外。引数非依存のルール（失敗率、平均所要時間、トークン異常、ターン数異常等）に絞る
  - `docs/requirements.md` §5.2 に「ファイル単位 / コマンド全文単位の分析」を Phase 1 スコープ外として追記
- **反映先**: `docs/requirements.md` §R1.6, §5.2 / `docs/functional-requirements.md` §F1.3.1, §F1.4.4, §F5.3

## 決定 6: セッションの境界定義

- **論点**: `/compact`, `/clear`, `--resume`, 長時間中断などを跨いだとき「1 セッション」をどう定義するか
- **決定**: **A — Claude Code の `session_id` に完全一致**。Gengar 側で時間ギャップ分割・論理セッション合成・コマンドマーカー分割は行わない。
- **根拠**:
  - 「純粋なメトリクスツール」「余計なものを管理しない」という方針に最も整合
  - Claude のモデルと 1:1 対応するため、JSONL との突き合わせ (R1.5) が自明
  - 時間ギャップしきい値などの設定項目を増やさずに済む
  - `--resume` で長く続くセッションは実際に「1 つの作業」として意味を持つため、分割の正当性は弱い
- **却下した代替案**:
  - B（しきい値で分割）: 設定値・論理 ID 付与など管理対象が増える
  - C（`/compact` / `/clear` で分割）: コマンドで区切る意味は薄い
  - D（Gengar 独自概念）: 最も複雑、他ツールとの整合性が崩れる
- **副次効果**:
  - ダッシュボードの「セッション所要時間」は、`--resume` を挟むと長時間になり得る。これは仕様として受け入れる
  - 平均ターン数・平均コストは「セッション 1 つあたり」= 「Claude session_id 1 つあたり」として素直に集計される
- **反映先**: `docs/requirements.md` §R1.7

## 決定 7: 並走時の整合性 — 追記型 + 単一ワーカーで吸収

- **論点**: 複数 `claude` プロセスが同時並走したとき、書き込み競合を防ぐための特別な要件が必要か
- **決定**: **独立した「並走サポート」要件は立てない**。代わりに **追記型アーキテクチャ + 単一ワーカー** を N7 として要件化することで自然に吸収する。
- **根拠**:
  - Gengar の目的は「いつ・何をしたか・いくらトークンを消費したか」の追記記録のみ
  - 追記専用なら hook が複数同時に起動してもレコード衝突は概念的に発生しない
  - 集計・オフセット更新など更新系の処理は 1 つのワーカー (`gengar daemon`) に集約すれば競合ゼロ
  - 排他制御やロックを明示する要件を書かず、設計原則で自然に解決する方が簡潔
- **却下した代替案**:
  - A（並走サポートを独立要件化）: 排他制御・WAL・ロック等の実装詳細に引きずられる。本質は「追記型」である点
  - C（サポート外を明記）: 現実のユーザー運用 (複数端末で並走) と合わない
- **反映先**: `docs/requirements.md` §N7

## 決定 8: タスクの成功/失敗

- **論点**: 「タスクが成功したか」を示す指標を持つか
- **決定**: **A — 追わない**。主観指標は Phase 1 では持たない。ツール失敗率 (`is_error`) のみ提供。
- **根拠**:

  - 代理指標はノイズが多く、手動ラベルは継続されない
- **却下した代替案**: B（代理指標）, C（手動ラベル）
- **反映先**: 要件側では明示的な条項を追加せず、F1.3 の計測項目から「成功率」を除外することで担保

## 決定 9: 公式 OTel との関係

- **論点**: Claude Code 公式 OTel (`CLAUDE_CODE_ENABLE_TELEMETRY`) を Gengar の入力源として取り込むか
- **決定**: **A' — Gengar が独自に OTel SDK を用いてメトリクスを emit する**。公式 OTel は前提としない。両者は独立に ON/OFF でき、並立可能。メトリクス名は `gengar.claude_code.*` prefix で衝突回避。
- **根拠**:
  - 公式 OTel 有効化はユーザーへの追加負担
  - Gengar は hook + JSONL で独自に収集できるため入力源として公式 OTel に依存する必要がない
  - OTel SDK を介すことで、Prometheus / SigNoz / 各種 OTel backend に横断で出力できる (ベンダー中立)
  - 公式 OTel と並立しても同じ backend に吸える (prefix 分離)
- **却下した代替案**:
  - B（公式 OTel を前提にし、JSONL からの補完のみ）: Gengar の適用範囲を狭めすぎる
  - C（公式 OTel を補完源として取り込む）: 両立サポートは複雑で MVP に不向き
- **反映先**: `docs/requirements.md` §R1 / §5.3 / `docs/functional-requirements.md` §F2

## 決定 10: ダッシュボード起動モデル — collector と UI を完全分離

- **論点**: daemon と UI を同居させるか分離するか。自作ダッシュボードを作るか
- **決定**: **分離する。自作ダッシュボードは作らず Grafana などの外部ツールに委譲**。Gengar は collector (hook + JSONL → OTel emit) に徹する。
- **根拠**:
  - Grafana / Prometheus / SigNoz などのエコシステムは成熟しており再発明する理由がない
  - Gengar の差別化は「Claude Code 特有の収集」にあり、UI はコモディティ
  - メンテナンス負荷が大幅に下がる
- **副次効果**:
  - R2 (可視化) が外部委譲に書き換え。R2.3「自作ダッシュボードは作らない」を明記
  - F3 (API サーバー) と F4 (ダッシュボード UI) を要件から削除
  - ユーザーは OTel backend + 可視化ツール (既存運用の Grafana 等) を用意する前提
- **反映先**: `docs/requirements.md` §R2, §5.2 / `docs/functional-requirements.md` 全面

## 決定 11: ネットワーク公開範囲

- **論点**: Gengar daemon のネットワーク露出をどう扱うか
- **決定**: **daemon は inbound ポートを基本持たない**。OTLP は outbound push なのでポート不要。`/metrics` exposition を選んだ場合のみ `127.0.0.1` 限定で出す。
- **根拠**:
  - push 型で完結するなら inbound ポート自体が不要
  - LAN 公開 / 認証 を考える必要がなくなり最小構成に合致
- **反映先**: `docs/functional-requirements.md` §F3.2.3

## 決定 12: UI 言語

- **論点**: UI / エラーメッセージの言語
- **決定**: **英語のみ**。i18n は Phase 1 ではやらない。docs は日本語のまま。
- **根拠**:
  - UI は外部ツール (Grafana) に委譲するため Gengar 側の文言は CLI / エラー / ログに限定される

## 決定 13: クエリエンジンは作らない

- **論点**: メトリクスのクエリ / 集計ロジックをどこで行うか
- **決定**: **Gengar はクエリエンジンを持たない**。PromQL / backend の query API に完全委譲。CLI / MCP も backend API の薄いラッパーとして実装する (post-MVP)。
- **根拠**:
  - Prometheus / VictoriaMetrics / SigNoz はいずれも強力なクエリ言語を持つ
  - 自作クエリエンジンは MVP を膨らませ、再発明になる
  - 自己改善ヒントは PromQL のプリセットとして同梱すれば十分
- **反映先**: `docs/requirements.md` §R3.4 / §5.2 / `docs/functional-requirements.md` §F5

## 決定 14: MCP と CLI の優先順位

- **論点**: CLI と MCP サーバーのどちらを先に作るか、両方 MVP に入れるか
- **決定**: **どちらも Phase 1 MVP (v0.1) には入れない**。v0.2 で CLI、v0.3 で MCP の順で追加する。

  - CLI / MCP は PromQL ラッパーで後から薄く載せられる
- **反映先**: `docs/requirements.md` §R3 (post-MVP) / `docs/functional-requirements.md` §F5

## 決定 17: 成功指標の測定可能性

- **論点**: §6 の「5 秒以内反映」「10 秒以内クエリ」「2 秒以内表示」をどう扱うか
- **決定**: **Phase 1 では数値目標を削除**。「体感で遅くないこと」「1 日使って困らないこと」に留める。実測値に基づく SLO は Phase 2 以降で設定する。
- **根拠**:
  - 測定条件 (マシン、DB 規模、warm/cold) が未定義で数値単独には意味がない
  - 計測インフラを先に整える工数が MVP に合わない
  - 実装後に実測して正直な数値を置く方が健全
- **反映先**: `docs/requirements.md` §7

## 決定 18: アーキテクチャのピボット — Gengar は Collector のみ

- **論点**: 決定 10, 13 の統合効果として、Gengar の全体アーキテクチャをどう定義するか
- **決定**: Gengar は **「hook + JSONL から OTel メトリクスを emit する collector」** に徹する。以下を**永久にスコープ外**として確定する:
  - 自作ダッシュボード UI
  - 自作 API サーバー
  - 自作ストレージ
  - 自作クエリエンジン
  - 保持期間・ロールアップなどのデータライフサイクル管理（backend の retention に委譲）
- **根拠**:
  - 観測スタック (OTel + Prometheus + Grafana) は十分に成熟しており、Gengar 独自価値は「Claude Code 特有のメトリクス収集」にある
  - スコープを collector に絞ることで、実装コストが 1/2 〜 1/3 に圧縮される見込み
  - ユーザーの既存 observability 運用とも統合しやすい
- **副次効果**:
  - R2 は「外部委譲」として書き換え
  - R4 は「backend 委譲 + ラッパー提供」に書き換え
  - F2 (旧ストレージ) / F3 (旧 API) / F4 (旧 UI) は要件から除去
  - 新 F2 は「OTel emit」、新 F3 は「セットアップ」、新 F4 は「self-observability」
  - Must スコープは大幅縮小され Phase 1 MVP が「動くところ」まで到達しやすくなる
- **反映先**: `docs/requirements.md` 全面 / `docs/functional-requirements.md` 全面書き換え
